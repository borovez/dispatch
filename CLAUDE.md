# Dispatch

Personal, local-only dashboard for pull requests across several GitHub orgs, with cross-repo
dependencies (merge-before / release-before), Jira status, and a Slack inbox. It also exposes an MCP
server so Claude Code can query and edit the same data.

## Run

Node lives in nvm and isn't on the default PATH: `export PATH=~/.nvm/versions/node/v24.13.1/bin:$PATH`.

- `npm run dev` (root) runs API `127.0.0.1:4317` (tsx watch) and Vite `localhost:5317` (proxies `/api`). The user usually has this running already; both hot-reload.
- `npm run mcp` runs the stdio MCP server. Settings → MCP shows the `claude mcp add` command.
- Typecheck: `npx tsc --noEmit -p server` and `cd web && npx vue-tsc -b`. Build: `cd web && npx vite build`.
- Installed app: the web app is a PWA (`web/public/manifest.webmanifest`, `sw.js` that caches nothing, registered in production only). `npm run app:install` builds and runs the server as a LaunchAgent (`dispatch.server`, port 4317, log `~/Library/Logs/Dispatch.log`); it conflicts with `npm run dev` on the same port.
- Data: SQLite at `~/.dispatch/dispatch.db` (`DISPATCH_DATA_DIR` overrides). Secrets are in the macOS Keychain (`server/src/secrets.ts`: `security` CLI, writes via stdin; service "Dispatch", accounts `github:<id>`, `jira`, `slack`, `launchdarkly`, `anthropic`); the settings row holds `keychain:` markers. `getSettings` resolves them (1-min cache) and migrates any plaintext secret (read back before blanking, then VACUUM + checkpoint; `secure_delete` is on); `saveSettings` writes changed secrets and deletes removed ones (keeps the marker if the keychain can't be read). `DISPATCH_KEYCHAIN=0` or non-macOS: secrets stay in the database. The API binds to loopback only and never returns tokens (masked as `hasToken`). `index.ts` also guards every request against browser pages on this machine: Host must be a loopback name (DNS rebinding), and writes need an Origin of Dispatch itself (its port or the Vite dev port) or none (curl, MCP), no `Sec-Fetch-Site: cross-site`, and a JSON body.

## Layout

- `shared/types.ts`: the contract for server, web and MCP. Change types here first.
- `server/src/`
  - `db.ts`: `node:sqlite` (WAL, shared by the API and MCP processes). Tables: kv (settings, sync state, UI prefs), prs, jira_issues, dependencies (manual), pr_meta (note/pin), slack_items.
  - `github.ts`: GraphQL search plus aliased batch fetch, checks (up to 100 runs per commit) from the latest run of each check only (`latestChecks`: per workflow, job and event; a run cancelled or failed and then replaced by a newer one no longer makes the PR "Fix CI", which GitHub's own rollup state still does), release detection (latest release/tag or a per-repo branch, via the compare API). Retries 5xx.
  - `jira.ts`: REST v3 (`/search/jql`), transitions, create (Markdown → ADF). Moved issues: Jira answers an old key (PLAT-158) with the issue under its new key (GROW-1333); `fetchIssuesByKey` and the panel's refresh record old → new in kv `jiraMoved` (Overview `jiraMoved`), `deck.jiraByKey` resolves old keys, the Jira page merges the rows, and the panel says "moved to …".
  - `slack.ts`: user token (xoxp). Pinned items (`slack_items.pinned`, `PUT /slack/:id/pin`; pin button in the Slack panel header, Pin to top in the Slack menu, `toggleSlackPin`) are never pruned, superseded or auto-closed, and show under Pinned at the top of the Inbox (and the Overview Slack panel) whatever their status, until unpinned. `syncSlack` (sync.ts) is the inbox fetch shared by the sync step and the Slack page's refresh button (`POST /slack/refresh`, Slack only). Sources: mentions (search.messages), unanswered DMs/group DMs, saved items (stars.list), todo reactions (reactions.list).
  - `ai.ts`: Claude drafts a Jira issue from a Slack thread. Provider `claude-code` (default) runs the local `claude -p` CLI with its own login via `claudeCode.ts` (safe mode, no tools, `--json-schema`; strip zod's `$schema`); provider `api` uses `@anthropic-ai/sdk` `beta.messages.parse` + zod with server-side fallbacks. Model default `claude-opus-5-5`.
  - `sync.ts`: single-flight sync. GitHub searches per account return ids only (`searchPrHits`, 100 per page, two searches at a time); results are deduped, then open PRs and changed merged/closed PRs get the full fields by node id (`fetchPrsByNodeId`, batches of 10, 4 in parallel); unchanged merged/closed PRs reuse the stored copy (checks and mergeability change without touching updatedAt, so open PRs are always fetched). Then dependency targets and PRs named by `Blocks:` lines (2 levels) and prune. A PR still not synced opens `UnsyncedPrPanel` (Sync this PR → `POST /prs/fetch`, Open on GitHub, what links to it). Slack runs alongside from the start; after the PRs are saved, release checks, LaunchDarkly and Jira run in parallel. Each step collects its own errors.
    Each stage is a step (`progress()`: queued, running, done, error, skipped; `note()` for "search 3 of 7") saved to the sync state as it changes; `GET /api/sync/status` serves it, the header's `SyncButton` polls it while a sync runs (manual, auto or MCP) and shows the steps in a hover card. A restart marks a stale `running` state stopped.
  - `model.ts`: `buildOverview()` derives everything: dependency edges (manual > PR body `Depends on:` / `Requires release of` > Jira "is blocked by"), satisfied/blocked, action and bucket per PR, dependency chains (topologically sorted connected components).
  - `routes.ts` (Hono, `/api/*`; imports the route modules in `routes/` (`core`, `settings`, `deps`, `prs`, `jira`, `slack`) in registration order (Hono matches in order; keep it); each registers on the shared `api` from `routes/shared.ts` (with `bad`, `jiraCfg`, `Images`). New routes go in the module for their area), `index.ts` (server + background sync loop; honours `settings.sync.auto` / `intervalMinutes`, toggled from the header via `PUT /api/sync/auto`), `mcp.ts` (17 tools; setup: `setup_status`, `update_settings`, `connect_github_gh_cli` from `settingsPatch.ts` (`SettingsPatch` zod schema of non-secret settings, also `PATCH /api/settings`; tokens can never be set by an agent); `jira_prompt` returns the agent brief; Jira writing: `jira_fields` (fields, choices, current values and description, writing guides), `create_jira_issue` and `update_jira_issue` take fields by name and choices by label via `resolveFieldInput` (exact, or an unambiguous partial match; otherwise they refuse and list the choices), check required fields, and refuse a description that drops the issue's `jira-media` images).
- `web/src/`: Vue 3 + TS, Pinia, vue-router, **shadcn-vue** (`components/ui/*`, generated, reka-ui based), Tailwind v4, Phosphor icons.
  - `stores/deck.ts`: overview data, selected PR (drawer), slackToJira (dialog).
  - `stores/layout.ts`: customizable dashboard panels (order, pin, collapse, width, sort, filter, limit), per-view state via `layout.view(name, defaults)`. Persisted to `/api/prefs`.
  - Overview panels (`stores/layout.ts` DEFAULT_PANELS): PR lists, Slack, Jira, chains (divided blocks with a chain icon, repos and "N of M done"; steps are `ChainStep` (status from `prStatus()` in composables/prStatus.ts, also used by the PR panel's Depends on / Blocks rows: each shows the other PR's status, and Blocks rows a check and "merged ✓" once this PR satisfies them): colour-coded chip (done green, merged awaiting release blue, next primary, else the action tone, not synced dashed) and a status hover card), releases (open releases with ship-next, hotfixes not back in dev, my unreleased work). New default panels are appended to saved layouts on load. The grid is `layout.zones`: a full-width panel spans both columns, runs of half-width panels are two column stacks (`column`, alternating when unset). Dragging a panel (handle) picks the nearest zone, so empty space under a short column or below the grid works, and a primary line shows the spot; `layout.place(id, ref, before|after, column)` applies it.
  - `components/`: PrRow, PrCard (compact card for graph nodes and the PR board), PrDrawer (resizable detail panel, add/remove dependencies), DashPanel (panel chrome), GroupCard (collapsible list section), SortDirButton, ActionBar (sticky bottom toolbar), SlackRow, SlackToJiraModal, JiraRow, JiraPill, JiraTransition, GraphNode.
  - `views/`: Dashboard, PullRequests, Slack, Graph, Jira, Settings.

## UI conventions

- Use shadcn-vue components wherever one fits. Add new ones with `npx shadcn-vue@latest add <name> --yes </dev/null`, then fix any `from 'cn'` imports to `from '@/lib/utils'` and `npm uninstall cn` if the CLI added it (a CLI bug).
- Local tweaks to generated components: `TabsTrigger` takes `count` (right-aligned badge), `TabsList` scrolls sideways when too wide (`max-w-full overflow-x-auto`), CardHeader stacks its CardAction under the title below `sm`, ContextMenuSubTrigger has `gap-2` like the items, `Alert` takes `closable` (emits `close`), `AlertAction` is vertically centred, Toggle/ToggleGroup on-state is primary, Switch off-track is visible in light mode, CardHeader has `gap-x-6` before a CardAction. SelectItem is square (`rounded-none`, flush with the list) with the picked item tinted primary, like the repo picker; don't round it per use. One hover card open at a time: the generated `HoverCard` wrapper (and `LinkHoverCard`) go through `useOneHoverCard` (composables/oneHoverCard.ts): opening one closes every other, except cards it sits inside (a card opened from within another card's content, or a link card from a link in one, keeps its parents); The innermost trigger under the pointer wins: `HoverCardTrigger` watches pointerover and tells its `HoverCard` (`./inner.ts`) when the pointer is on an inner trigger (`innerTrigger` in lib/hoverTargets.ts: a nested card's trigger, or a link the link card serves, `linkCardTarget`); the outer card then closes or won't open, and reopens after its delay when the pointer is back on its own area. `HoverCard` keeps `open: undefined` as its default so it stays uncontrolled, and emits update:open itself. Keep all this when regenerating them. Tooltip, Popover, HoverCard and ContextMenu (root, trigger, content) read `useArmed()` (`composables/arming.ts`): inside a list row that isn't armed yet they render only the trigger element; keep that when regenerating them.
- A menu or popover button with a tooltip: put the `Tooltip` around the whole `DropdownMenu` / `Popover` (`TooltipTrigger as-child` on a `<span class="inline-flex">` holding it), never `DropdownMenuTrigger` inside `TooltipTrigger`: both attach to the nearest popper context, so the menu's trigger anchors to the tooltip and the menu stays unpositioned off screen (`translate(0, -200%)`). ShareMenu, the panel history button and the Slack @mention button follow this.
- Writes go through `deck.mutate(fn, successMsg?)`: it toasts errors (and the success message), reloads, and returns whether it worked. Don't keep per-component error state for writes. Transient feedback is a toast (vue-sonner, `toast` from 'vue-sonner'); alerts are for persistent state.
- Markdown inputs use `MarkdownEditor` (one bordered box: formatting toolbar from `formatActions()` with GitHub shortcuts, Preview toggle (always opens in edit mode, not remembered); fixed height with a `ResizeHandle` grab bar (`v-model:height` to keep it) / `grow` / `fill`, `strike`, `mono`; `#toolbar` slot for extra buttons, `#preview="{ value }"` for another renderer (default the Jira ADF view), `keydown` re-emitted for Enter-to-send etc.). Used by the Jira description and text fields, the writing guide, the PR note and writer, the agent prompt and the Slack reply. Plain prompts (`AiPromptBox`) and JQL stay plain.
- Resizable sections: `ResizeHandle` (grab bar, `line` for a divider line, `invert` for a bar above its section; v-model px, drag / arrow keys, double-click resets; `target` is measured when a drag starts). `SidePanel` `v-model:footer-height` (0 = fit) makes the line above the footer draggable. PR panel (`layout.view('drawer')`): the footer line sizes the footer and My note fills it (`footerHeight`, only while the note is open), the line between Dependencies and My note sizes the list (`depsHeight`, 0 = fit), and the note fills what's left; with the note closed the footer line still drags (`closedFooterHeight`, 0 = fit) and the Dependencies list fills the footer; neither line can squeeze the note below `NOTE_MIN` (`SidePanel` `footerMin`, `ResizeHandle` `maxAt`, both measured when a drag starts). Slack panel: the line above the reply box sizes it (`layout.view('slack-panel').replyHeight`, 0 = grows with the text).
- In-app vs external links: a plain click on a PR, Jira issue or Slack item opens it in Dispatch (side panel); Cmd/Ctrl-click opens the outside site (`openInAppOr`, `wantsExternal`, `modClickHint` in `lib/external.ts`; rows say so in their tooltip). A link that only goes outside is an `ExternalLink` (↗ after the text, on hover or `icon="always"`; tooltip "Opens GitHub in a new tab ↗", "in your browser" in the Mac app; `label` for text before it; stops the click reaching the row). Only external links underline; in-app links use hover colour or background. Icon buttons that open a site use `PhArrowSquareOut` with `externalHint(url)` as their tooltip.
- Link hover card (`LinkHoverCard`, mounted once in App.vue): hovering any link out of Dispatch (absolute `http(s)` href on another origin; sidebar and router links never) (PR / Jira descriptions, Slack text, `ExternalLink`…) for ~0.5 s shows the full URL (Copy), what it is from the URL and Dispatch's data (`describeLink` in lib/linkInfo.ts: PR status, Jira status / assignee, Slack author, flag environments, GitHub file / commit / compare / release…; "Open in Dispatch" for known items), then fills in from `GET /api/link-preview` (`server/src/linkPreview.ts`: GitHub PRs / issues / repos via the GitHub API, Jira issues via Jira, other pages' title / description / Open Graph image / icon; page fetches refuse loopback and private addresses on every hop (checked in the connection's DNS lookup), no cookies, 512 KB / 6 s; cached an hour). The link's own `title` is hidden while it shows. Opt out with `data-no-link-preview`.
- PR hover preview (`PrHover` → `PrPreview`, on PR rows and cards) uses the link hover card's layout: GitHub · Pull request with the `prStatus` badge, title, repo / author / updated, what it does (`descriptionSummary` in prDetail.ts: a Summary / Description / What-and-why section, else the text before the first heading, else the first section that isn't bookkeeping like JIRA, Stack, Deployment, Testing), a muted box with branch → base, files / +/− with a ratio bar and the 3 biggest files, then Open / GitHub / Copy.
- Suggestion lists (pickers, menus, search: FilterMenu, GlobalSearch, MultiPicker, PrListPopover, PrPicker, JiraFieldChip) move with `useListNav` (composables/listNav.ts): Up / Down wrap, skip `disabled` rows, nothing on an empty list, clamp when the list shrinks, scroll the `data-active` row in `container` into view. Enter and other keys stay with the component. Use it for any new keyboard list.
- Clipboard: always `writeClipboard` (`lib/clipboard.ts`; `copyText` in itemMenus.ts toasts): it copies synchronously in the click through a `copy` event (`navigator.clipboard` alone can hang forever from a menu item, so nothing happened), async API as a 2 s fallback.
- Page-level save/actions live in `ActionBar` (sticky bottom), not floating buttons.
- Tracked repos (Settings → GitHub) are picked with `MultiPicker` from the repo catalog (`server/src/repoCatalog.ts`, `GET /setup/github/repo-catalog`): every repo of every account's orgs (or the orgs an account is limited to), all pages, stored in kv for an hour (survives restarts), `?refresh=1` from the refresh button; typed `owner/name` can still be added.
- Settings: state in `stores/settings.ts` (page form + `saveSection(patch)` for one section on top of the last saved copy). Integrations are `components/settings/*` built on `ConnectionCard` (read-only details; Connect, or Edit + Disconnect) with `FormDialog` (draft, Test, Save). Destructive confirms use `ConfirmDialog`. Form fields use `Field`.
- Global search (`components/GlobalSearch.vue`): `/` or Cmd/Ctrl+K opens a palette over PRs, Jira issues, Slack messages, pages and actions; groups are ordered by their best match.
- Escape closes custom panels via `onEscape(fn)` (`composables/escape.ts`); reka dialogs/menus handle their own. Side panels use `SidePanel` (resizable, Escape; wheel never scrolls the page behind it; while one is open the page scrollbar is hidden via `html.side-panel-open`, padded by its measured width so nothing shifts). Panel history (deck store: `panelBack` / `panelForward`, `panelGo`): every switch to another PR, Jira issue or Slack message is an entry; the history lasts the session (in memory, 50 each way; a reload keeps the open panel and its history: per tab in sessionStorage `dispatch.panel`, restored once the overview has loaded): closing keeps it and the next item opened gets the closed one as Back; `PanelHistoryNav` in the `SidePanel` top bar (one row on every panel: back / forward left; the panel's `actions`, keep open, close right; the `header` slot below it) (back / forward with the target in the tooltip, Alt+← / Alt+→, mouse back / forward buttons; a history button (always on while a panel is open) lists every entry, forward above Now above back, then Recently opened, picking one jumps there via `deck.panelJump(steps)`, the highlighted entry (mouse or arrow keys) shows one look-only `PanelItemCard` beside the menu: the PR preview without its buttons, or link-card details for Jira / Slack; one shared card, not a hover card per entry, which stacked up). Each panel's top bar has `ShareMenu` (copy link, link with title as rich HTML, Markdown, key / reference, title, system Share… where `navigator.share` exists; toast plus a check on the button). Jira issue-type icons go through `jiraIcon()` (utils/format.ts: `size=xlarge`, Jira's `medium` is a blurry 16px PNG). Each panel's title starts with a `KindIcon` (pull request, Jira issue, Slack message; icons and tints in `utils/itemKinds.ts`, the sidebar's page icons), and the back / forward tooltips show the target's icon. Moves through a list (arrow keys, Done → next) go through `deck.replacePanel(fn)` so they don't add entries. Recently opened items (`deck.recentPanels`, newest first, 15, in `layout.view('recent-panels')`): while no panel is open, `PanelTab` is a slim tab on the right edge; hover slides out the last item and five earlier ones, click or Alt+→ reopens (`deck.reopenPanel`). With one open, Arrow Up/Down moves through visible `[data-pr-id]` / `[data-slack-id]` elements in on-screen order (`useArrowNav` in `composables/prNav.ts`); put the attribute on any new PR or Slack item.
- reka-ui sets `data-state`, the generated classes use `data-checked:` etc.; `style.css` maps them with `@custom-variant`. Keep that block when regenerating components.
- Colours only via theme tokens in `web/src/style.css` (zinc + indigo; light, `.dark`, and System via `useTheme()`). Status tokens: `success`, `warning`, `info`, `merged`, `destructive`. Badge has matching soft variants (`primary|success|warning|info|merged|muted`). Never hard-code colours. Check both themes.
- Persist user view choices through `useLayout().view(...)`, not localStorage.
- List toolbars (Linear-style): `FilterMenu` (popover: search fields and values, open a field to tick several, F opens it; options carry counts given the other filters, `hint` for muted text like a repo's org) with `ActiveFilters` chips in a row under the toolbar; `DisplayMenu` (popover: List/Board switch, select / order+direction / switch rows, display-property pills that store the hidden ones). The PRs page uses them (`v.filters`, `v.hidden` → `PrRow :hide`); other pages still use the older `ViewMenu` dropdown.
- Long lists render every row (no virtualization). Rows stay cheap instead: the root gets `lazy-row` (`content-visibility: auto`, style.css) and calls `useRowArming(rootRef)`, so its menus, hover card, tooltips and popovers mount only once it nears the viewport (shared IntersectionObserver, 800px margin) or is hovered or focused (focus is put back after the re-render). `PrRow`, `JiraRow`, `SlackRow` and the PR board's `BoardCard` (PrCard + hover preview) do this; do the same for any new row type. Not for graph nodes (Vue Flow measures them).
- List rows are inset rounded inside the card's padding (`GroupCard` / `DashPanel` / `p-1.5`), never flush with dividers: `rounded-lg px-3 py-2.5 transition-colors hover:bg-accent`, selected `bg-accent ring-2 ring-primary ring-inset` (`PrRow`, `JiraRow`, `SlackRow`, release contents, Overview panel rows). Only group headings (e.g. Slack's day bars) span the card.
- Right-click menus: `ItemContextMenu` (shadcn ContextMenu, `display: contents` trigger; Shift+right-click or selected text keeps the browser menu) around an item, with entries from one definition per item type in `composables/itemMenus.ts` (`usePrMenu` + `.byId`, `useJiraMenu`, `useSlackMenu`; `MenuEntry`: action with `run`/`href`, `hint`, `children` or an async loader for submenus, `'separator'`, `{ heading }`). Used on `PrRow`, `JiraRow`, `SlackRow` and the items listed in the side panels (dependencies with Remove, linked issues, banner links; "Open in panel", none for the item already shown); the dependency and release graphs (cards, release headers, rows; right-clicking a dependency edge opens its edge card), and reuse the same entries for any other place that offers those actions.
- A PR's checks are a `ChecksChip` (PR panel): one chip coloured by state ("2 of 60 failing", "60 passing", Running, No checks) that opens the failing checks (ScrollArea, each links to its run) and All checks on GitHub.
- A count of PRs is a `PrListPopover` chip ("N PRs", `compact` for the count only): opens a filterable list (arrows, Enter opens the PR panel; `fallback` for untracked PRs opens GitHub; `numbered`/`highlight`; `#detail` slot for extra lines). Used for release contents (PrRow, PrCard; `hide: ['contents']`), Jira linked PRs (Dashboard, dense Jira rows) and PRs naming a flag (`useFlagPrs`: FlagChip, FlagStatus popover, FlagList).
- List pages (Pull requests list, Slack, Jira) are `max-w-6xl` (Releases is full width, list and graph); Settings is a narrower form (`max-w-4xl`); the Overview grid and full-height views use the full width.
- Pages scroll the window (native scrollbar at the window edge, like Settings), not an inner `ScrollArea`; sticky things sit under the `h-14` header (`top-14`). List pages (PRs, Jira, Slack, Releases) put their toolbar in `StickyToolbar` (stays under the header, page background over `<main>`'s padding, border once stuck; use it in a flex column with gap); it sets `--sticky-top` (header + toolbar), so sticky things below it use `top-(--sticky-top,--spacing(14))` (Slack's day headings). ## Pages

### Dependency graph (`/graph`)

`views/GraphView.vue` + `components/GraphNode.vue` (Vue Flow + dagre LR). Edges drawn prerequisite → dependent (solid merge, dashed release; green/muted satisfied, amber waiting). Repo tabs like the release graph (both use the `RepoSelect.vue` dropdown, counts on the right; `v.repo`, '' = all): a repo's PRs in the chains shown plus the PRs in other repos they directly depend on or block (`linkedIds`, dashed and faded cards); counts are open PRs. Org / finished / mine filters and unlinked PRs persist via `layout.view('graph', …)`. Drag right handle → left handle creates a dependency: a card at the drop point (dashed preview edge) asks Merged (M) / Released (R), Escape or a pane click cancels; the last choice is the highlighted default (`v.newKind`); click an edge to see it and delete manual ones. "Unlinked PRs" shows open PRs without deps so links can be drawn to them. Vue Flow is themed in the view's unscoped `<style>` (`.dep-graph`).

### Feature flags (LaunchDarkly, read only)

PRs name flags in their description: `Feature flag: key` / `Flags: a, b` lines (colon required; with backticks only the backticked keys count), qualified prose ("`key` LaunchDarkly flag", "feature flags `a` / `b`"), or LaunchDarkly flag links (`parseFeatureFlags` in refs.ts; `PrView.flags`). Sync step 4c (`launchdarkly.ts`, GET only) caches each referenced flag's on/off per configured environment (`feature_flags`, Overview `flags`). UI: `FlagStatus` (rows/cards), `FlagList` (PR panel), `FlagChip` (release contents roll-up), flag icon on release graph rows, `settings/LaunchDarklySettings.vue` (Reader access token, project key, environments).

### Dependencies written to GitHub

Adding a dependency (PR panel, graph) edits the dependent PR's description on GitHub (`bodyDeps.ts`: fetch the current body, add `Depends on: org/repo#N` / `Requires release of: …`, PATCH), so the edge's source becomes `body`. Removing a `body` edge takes the ref out of that line. With `writeBothSides` the prerequisite also gets `Blocks: A` / `Release blocks: A` (`withBlocks`; read back by `parseBodyBlocks`), and removing takes both lines out. If neither write works, the dependency is stored as manual and the toast says why. `settings.dependencies.writeToDescription` / `writeBothSides` (Settings → Dependencies) turn this off; Overview `dependencyWrites` exposes them. Web side: `composables/dependencies.ts` (one write per pair at a time, shared `busy` for disabling controls, existing dependencies skipped; module-level undo / redo history of adds and removes (30), Undo / Redo on each toast, undo / redo buttons and ⌘Z / ⇧⌘Z on the dependency graph; `writing` lists writes in flight, drawn on the graph as grey dashed moving links labelled Adding… / Removing…; undoing a removal adds it back through the usual write, so a removed manual dependency may come back in the description). PRs are picked with `PrPicker` (title/repo/number/branch/Jira search; `filter`, `disabledReason` for already-linked PRs) in the PR panel (`DepAddForm`: + Add on each of its two lists, "Waits for" and "Waiting on this PR", so the list sets the direction; only merged / released is chosen, and a sentence with the real PR numbers says what gets recorded), the graph's Add dependency form and the Release train section. The MCP `add_dependency` tool still stores manual deps.

### Releases (`/releases`)

`views/ReleasesView.vue`. `server/src/flow.ts` classifies PRs (`PrView.flow`): release (dev/release/* → master/main), hotfix (other branches → master/main in repos that use dev), backmerge (master → dev). Release trains (`buildTrains` in model.ts, Overview `trains`; a wait inherited through contents reads "ships X, which needs Y merged"; open releases nothing in the train must precede are marked "can ship any time"): open releases across repos linked by dependencies between their contents (ordered, topological) or shared Jira issues (unordered); Trains tab (`TrainCard`); the order is set in the PR panel's Release train section (`TrainOrder`: the releases as a list, drag a handle to reorder; the drop becomes a plan (descriptions gaining / losing `Depends on:` lines) applied on Apply: a merge dependency per consecutive pair, contradicting direct ones removed; merged releases stay first, orders from the contents can't be reversed; Show in graph → Trains graph (`openTrainGraph`); ship after another release via `PrPicker`, remove order). Releases are colour coded by `useReleaseStatus` (composables/trainStatus.ts: merged, waits for an earlier release, ready to merge green, else the PR's action tone): a bar and badge in `TrainOrder`, the step number in `TrainCard`, the action badge of `PrCard` (dependency graph, PR board) for releases in a train (train icon), and a badge on the right of each open release card on the Releases tab (with Ship next for its train's next release; `useReleaseStatus(null, id)` outside a train), dotted "same Jira" edges in the graph, a line in the PR panel banner. ## Pull request dependencies, feature flags and deployment steps

When opening or editing a pull request (in this repo, and in the repos Dispatch tracks), declare ordering in the description, one kind per line, always with the full `owner/repo#number` (never a bare `#12` for another repo, never only a URL). These are the formats Dispatch itself reads (`server/src/refs.ts`):

- `Depends on: owner/repo#12`: this PR merges only after owner/repo#12 is merged.
- `Requires release of: owner/repo#34`: this PR needs owner/repo#34 released (deployed), not just merged.
- `Blocks: owner/repo#56`: owner/repo#56 waits for this PR's merge (the other side of its "Depends on").
- `Release blocks: owner/repo#78`: owner/repo#78 waits for this PR's release.

Rules:

- Several PRs of the same kind go on one line, comma separated (`Depends on: owner/api#12, owner/web#40`); don't repeat the label.
- Write both sides: `Depends on:` here and `Blocks: <this PR>` on the other PR (`Requires release of:` / `Release blocks:` for release dependencies). Fetch its body with `gh pr view <n> --repo <owner/repo> --json body --jq .body`, change only that line, write it back with `gh pr edit <n> --repo <owner/repo> --body-file <file>`. No access? Say so.
- When a dependency goes away, remove it from both PRs and drop empty lines. Never remove or reword dependency lines someone else wrote unless asked.
- Before opening a PR, check whether it needs another repo's or open PR's change; ask if unsure; with none, leave the lines out (no "Depends on: none").
- Release PRs (dev → main/master, `release/*` → main/master) that must ship after another repo's release get `Depends on: <that release PR>`, and that one gets `Blocks: <this release PR>`.
- Feature flags: `Feature flag: flag-key` (several: `Feature flags: flag-a, flag-b`), exact key; for a new flag, say its default and what turning it on does.
- Deployment steps: every PR has a `## Deployment steps` section, an ordered `- [ ]` checklist of what shipping it takes, in order: what deploys first (matching the dependency lines), config/env to change (names only, never values), migrations (safe with the old code live?), commands or backfills, flags to turn on and where, what to verify, how to roll back (and what can't be undone). Nothing special: `None: a normal deploy.`

The PR template (`.github/pull_request_template.md`) has these sections.

## Releases and updates

Version in the root `package.json` (`VERSION` in `server/src/updates.ts`; `/api/health` reports it). `npm run release -- patch|minor|major` (scripts/release.sh, from a clean `main`) bumps, tags, pushes and creates a GitHub Release with `gh`. The server checks `releases/latest` of the repo at start and every 6 h (cached in kv `updateCheck`): anonymously, then with each GitHub token in Settings and the gh CLI login (`repoApi`), so it works if the repo is private and the user has access (otherwise it reports it can't see the repo); `GET /api/update` adds whether this install can update itself (a git checkout, no local changes, `NODE_ENV=production`, i.e. the LaunchAgent). `POST /api/update` runs `scripts/app-update.sh` detached (pull --ff-only, npm install, build, `launchctl kickstart -k`; log `~/Library/Logs/Dispatch-update.log`); the web app polls `/api/health` for the new version and reloads (`composables/updates.ts`, `UpdateButton.vue` in the header, version and Check for updates in `NavUser`). The version also shows beside the app name (`AppVersion.vue`, dot when an update is out); a new version is announced once with a toast (Update / Download / View release, What's new opens the header popover; remembered in `layout.view('updates').announced`). Mac app: `desktop/` (Electron 45, Node 24 so `node:sqlite` works). `scripts/bundle.mjs` builds the web app into `desktop/app/web` and bundles `server/src/index.ts` and `mcp.ts` with esbuild into `desktop/app/server/*.mjs` (ESM with a `require` shim); the app's version follows the root `package.json`. `main.mjs` reuses a server already answering on the port (the LaunchAgent) or runs the bundle with `ELECTRON_RUN_AS_NODE` (`DISPATCH_WEB_DIR`, `DISPATCH_VERSION`, `DISPATCH_INSTALL=desktop`, a PATH with `~/.local/bin` and Homebrew; log `~/Library/Logs/Dispatch-desktop.log`), opens a window on it, sends external links to the browser, and checks for updates through the local server's `GET /api/update` (so private-repo access works; native dialog → the matching `.dmg`; menu Check for Updates…). Icon: `desktop/build/icon.svg` (macOS grid: 824px rounded square on 1024, shadow) rendered to `build/icon.png` (headless Chrome); run from source the Dock icon and name are set in `main.mjs`. Lock: `lock.html` + `preload.cjs` (`window.dispatchLock.unlock()` → `systemPreferences.promptTouchID`, else the macOS admin password dialog via osascript) on open, on `lock-screen` / `suspend`, and Lock Now (⌘L); Dispatch → Require Unlock (userData `prefs.json`). Unsigned (`identity: null`), `asar: false` so the bundle runs as plain files; `electronVersion` pinned. Desktop installs report `canSelfUpdate: false` with the release's `downloadUrl` (the banner shows Download). `npm run release` builds and uploads the `.dmg`s. Not done: Developer ID signing / notarization and silent updates, the embedded GitHub/Jira pane from `docs/tasks/electron-embedded-browser.md`, an MCP command for desktop-only installs (the bundle has `mcp.mjs`).
